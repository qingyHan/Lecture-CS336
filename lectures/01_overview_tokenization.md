> tokenization"\

## Part 1 --- 本讲定位：为什么要从零构建语言模型？

### 1.1 课程真正要训练的能力

把模型 API 调通，与理解语言模型为什么能工作，是两种不同的能力。高层 API
把 tokenizer、模型结构、训练数据、优化器、GPU kernel
和推理服务隐藏在接口后面；当结果异常、成本过高或需要研究新方法时，这些抽象会暴露边界。

CS336 的主线是 **通过构建理解（understanding via
building）**。我们不只问"这个模型效果怎样"，还会问：

-   它接收的原始数据是什么，怎样变成模型输入？
-   模型每层执行什么数学运算？
-   一步训练需要多少计算、内存和通信？
-   数据、模型结构和硬件选择怎样影响质量与成本？
-   观察到的提升究竟由哪个变量导致？

课程不是要求在个人电脑上复现前沿大模型的完整训练成本。我们会在小规模上验证算法机制，再用公式、公开材料和受控实验推理大规模行为。

### 1.2 语言模型的最小数学定义

给定 token 序列 (x_1,`\ldots`{=tex},x_T)，自回归语言模型把下一个 token
的条件概率建模为

\[ p\_`\theta`{=tex}(x_1,`\ldots`{=tex},x_T)
=`\prod`{=tex}*{t=1}\^{T}p*`\theta`{=tex}(x_t`\mid `{=tex}x\_{\<t}). \]

-   (x_t)：第 (t) 个 token 的整数 ID。
-   (x\_{\<t})：当前位置之前的 token。
-   (`\theta`{=tex})：模型可学习参数。
-   (p\_`\theta`{=tex}(x_t`\mid `{=tex}x\_{\<t}))：在已知前文时，对下一个
    token 的概率分布。

训练通常最大化训练文本的对数似然，等价地最小化负对数似然：

\[ `\mathcal{L}`{=tex}(`\theta`{=tex})
=-`\sum`{=tex}*{t=1}\^{T}`\log `{=tex}p*`\theta`{=tex}(x_t`\mid `{=tex}x\_{\<t}).
\]

本讲先不推导 Transformer
或优化器。我们先解决一个更基础的问题：**序列里的 (x_t) 究竟是什么？**

## Part 2 --- Tokenization 要解决的问题

### 2.1 模型为什么不直接接收字符串？

神经网络的矩阵运算需要数值张量。原始文本却是 Unicode
字符串。Tokenization（分词/切
token）负责把字符串转换成整数序列；模型再通过 embedding 等组件，把整数
ID 映射成可计算的向量。

\[ `\text{文本字符串}`{=tex}
`\rightarrow `{=tex}`\text{token 序列}`{=tex}
`\rightarrow `{=tex}`\text{token IDs}`{=tex}
`\rightarrow `{=tex}`\text{向量表示}`{=tex}
`\rightarrow `{=tex}`\text{模型}`{=tex} \]

注意：**token ID 不是 token 的语义数值**。如果 token "cat" 的 ID 是
17，而 "dog" 的 ID 是 18，并不意味着 dog 比 cat
大，也不意味着它们语义相差 1。ID 只是查表用的离散索引。

### 2.2 Token 不等于单词

在常见的子词 tokenizer 中，一个 token 可能是：

-   一个完整的常见单词；
-   单词的一部分；
-   一个空格加单词的一部分；
-   标点；
-   数字片段；
-   多字节字符的一部分所对应的字节片段（对 byte-level tokenizer 而言）。

因此，不能通过 token 数直接推断自然语言的词数。不同语言、不同
tokenizer、不同文本格式的 token/字符比例都可能不同。

## Part 3 --- 四种表示方式的取舍

### 3.1 字符级（character-level）

把 Python 字符串拆成 Unicode code point：

``` python
list(map(ord, "Hi!"))  # [72, 105, 33]
```

优点：直观；词表比词级词表通常小。\
缺点：字符集合可能很大；每个字符单独成为一个位置，序列通常较长。Unicode
code point 也不等同于用户看到的"一个字形"：某些 emoji
或组合字符可能由多个 code point 构成。

### 3.2 UTF-8 字节级（byte-level）

先把字符串编码为 UTF-8，再把每个字节作为 0--255 的整数：

``` python
"🌍".encode("utf-8")
# b'\\xf0\\x9f\\x8c\\x8d'
```

优点：基础词表固定为 256 个可能的字节值；任何合法 UTF-8
文本都能被表示，不需要为每个新词准备 UNK。\
缺点：一个 Unicode
字符可能占多个字节；序列会比子词序列更长，增加模型处理的位置数。

字节级表示的"无未知文本"性质不等于"任何任意字节序列都能直接解码成合法
Unicode 字符串"。编码和解码仍需要遵守 UTF-8 规则。

### 3.3 词级（word-level）

把文本按词或空白切开，每个词分配一个 ID。

优点：常见词通常只占一个 token，序列较短。\
缺点：词表容易膨胀；罕见词、拼写变体、专有名词和新词会带来词表外（OOV）问题；不同语言的分词规则也不一样。

### 3.4 子词级（subword-level）与 BPE

BPE（Byte Pair
Encoding）从小单位开始，统计相邻单位对的频率，并反复把高频相邻对合并成新单位。它让常见片段用较少
token 表示，同时保留把罕见词拆成更小片段的能力。

  --------------------------------------------------------------------------------------------------
  表示方式                        基础词表 序列长度倾向   未见新词           主要代价
  ------------- -------------------------- -------------- ------------------ -----------------------
  字符级                    与字符集合有关 中到长         通常可拆分         字符表/序列长度

  UTF-8 字节级                256 个字节值 通常很长       可表示合法 UTF-8   模型要处理更多位置
                                                          文本               

  词级            取决于训练语料，可能很大 通常较短       可能 OOV/UNK       大词表、稀有词问题

  BPE 子词级      由基础符号与合并次数决定 通常较短       可回退到更小单位   需要训练/保存
                                                                             tokenizer，切分有偏差
  --------------------------------------------------------------------------------------------------

这里的"通常"很重要：没有一种 tokenization
在所有语言、任务和模型规模下都绝对最好。

## Part 4 --- 从零推导一个玩具 BPE

### 4.1 算法定义

假设我们把输入文本先变成初始符号序列。byte-level BPE 的教学简化版本从
UTF-8 字节开始。

每轮执行：

1.  遍历训练语料中每个序列，统计所有相邻 token pair 的出现次数。
2.  选取频率最高的 pair ((a,b))。
3.  创建新 token (c)，使其字节内容为 (v(c)=v(a)`\Vert `{=tex}v(b))，其中
    (`\Vert`{=tex}) 表示字节串拼接。
4.  把序列中所有从左到右、互不重叠的 ((a,b)) 替换为 (c)。
5.  重复，直到达到合并次数或词表预算。

这是教学版算法。真实 tokenizer
往往会先按正则规则切分文本，避免任意跨越所有字符边界地合并；高性能训练实现也会使用更高效的数据结构。课程第一讲的源码用于展示基本机制，而不是完整生产
tokenizer 的所有规范。

### 4.2 数值例子：训练文本 `ababab`

初始字节序列是：

  -----------------------------------------------------------------------------------------------
  轮次              序列               高频相邻对                               操作
  ----------------- ------------------ ---------------------------------------- -----------------
  初始              `a b a b a b`      `(a,b)` 出现 3 次；`(b,a)` 出现 2 次     选择 `(a,b)`

  Merge 1           `[ab] [ab] [ab]`   新 token `ab` 与 `ab` 相邻两次           把两个相邻 `ab`
                                                                                合并为 `abab`

  Merge 2           `[abab] [ab]`      已无需要继续的相邻对（本例已演示目标）   停止
  -----------------------------------------------------------------------------------------------

为了精确描述 token ID：初始字节 `a`、`b` 的 ID 分别是 97、98。第一次
merge 新建 ID 256，内容为 `b"ab"`；第二次 merge 新建 ID 257，内容为
`b"abab"`。编码 `ababab` 的结果是 `[257, 256]`，解码时拼接
`b"abab" + b"ab"`，还原为 `ababab`。

这个例子展示了 BPE 的关键性质：合并结果依赖训练语料的统计频率与 merge
顺序。BPE 学到的是有利于压缩序列的片段，不保证每个 token
都是语言学意义上的词根、词缀或完整单词。

### 4.3 为什么 merge 顺序必须保存？

假设训练时先学到 `(a,b) → ab`，再学到
`(ab,ab) → abab`。推理时必须按相同的合并顺序处理输入，否则就可能得到不同的
token 序列。token ID 与模型 embedding 的行一一对应，因此更换 tokenizer
不能简单视为不影响模型的预处理小改动。

## Part 5 --- Token 数量为什么是系统问题？

设原始 UTF-8 文本有 (B) 个字节，tokenizer 将其编码成 (T) 个
token。可以用

\[ r = `\frac{B}{T}`{=tex} \]

表示每个 token
平均承载多少字节（这里只是一个简单的压缩指标，不代表语义质量）。

-   \(T\) 越小，同样文本通常只需更少的 token embedding 和输出位置。
-   在标准稠密自注意力中，序列长度相关的注意力计算/中间矩阵通常具有
    (O(T\^2)) 项；把 (T) 缩短会显著影响注意力成本。
-   但 Transformer 的前馈网络等部分通常还含有 (O(Td\^2))
    计算，因此不能把整个模型的总成本简单说成只与 (T\^2) 成正比。
-   tokenizer 也会影响输出序列长度：同一段文本被切成更多 token
    时，自回归生成通常需要更多预测步。

因此，tokenization
不只是语言学预处理，它会影响词表参数量、上下文容量、训练计算量、推理延迟和数据管线。

## Part 6 --- 从数学定义到代码

运行：

``` bash
python code/tokenization_demo.py
python -m unittest discover -s tests -v
```

代码只依赖 Python 标准库，适合 CPU 环境。它实现：

-   `CharacterTokenizer`：Unicode code point 与整数互转；
-   `ByteTokenizer`：UTF-8 bytes 与整数互转；
-   `ToyBPE`：统计 pair、执行 merge、编码和解码。

先检查两个不变量：

1.  对可往返的输入字符串，`decode(encode(text)) == text`。
2.  BPE 训练产生的新 token 保存的是原始字节片段，因此解码可以通过拼接
    token 对应的 bytes 还原原文。

**正确性与效率必须分开。**
本教学实现使用简单的计数和序列扫描，目的是清楚呈现算法。大语料上的高性能
BPE 训练需要更高效的 pair
计数更新、数据分块和并行化；不能用玩具实现的运行时间推断生产 tokenizer
的速度。

## Part 7 --- 官方实现与教学实现的关系

本讲主要对照官方 `lectures/lecture_01.py` 中的内容：

-   `CharacterTokenizer` 使用 `ord` / `chr`；
-   `ByteTokenizer` 使用 UTF-8 编码、`bytes` 与整数；
-   `merge` 把指定的相邻 pair 替换为新 ID；
-   `BPETokenizerParams` 保存词表与 merges；
-   `BPETokenizer` 使用保存的 merges 进行编码，并用词表中的 bytes 解码；
-   讲义明确指出其简单 BPE 编码实现较慢。

本项目代码是独立的教学实现，接口和例子为可运行性做了简化，不是 Stanford
staff code 的复制品，也不是对官方作业的提交答案。

## Part 8 --- 实验：词表与序列长度的权衡

**实验问题**：增加 BPE merge 次数是否会减少同一训练文本的 token 数？

-   假设：在训练语料固定时，继续合并不会增加该语料已编码序列的长度；一般会减少或保持不变。
-   基线：0 次 merge，即字节级表示。
-   自变量：merge 次数。
-   控制变量：语料、文本边界、编码逻辑、统计口径。
-   指标：token 数、平均 bytes/token、词表大小。
-   验证：用代码对同一文本在不同 merge budget 下编码并记录结果。
-   限制：在训练语料上 token
    数变少，不代表验证集压缩、模型质量或端到端速度一定改善；还需要单独测量。

本项目首个自动化测试验证 round-trip 和两轮合并；"不同 merge
次数的统计曲线"作为后续可扩展实验，不在没有运行的情况下宣称已有实测结果。

## Part 9 --- 常见误区与失败模式

1.  **把 token 当作单词。** Token
    可能是词的一部分、空格、标点或字节片段。
2.  **把 token ID 当作连续数值。** ID
    是离散索引，不能直接做语义大小比较。
3.  **把字符和 UTF-8 字节混为一谈。** `len(text)` 与
    `len(text.encode("utf-8"))` 可能不同。
4.  **只训练 BPE 不保存 merge 顺序。** 编码可能不一致。
5.  **把 `merge` 当作任意子串替换。** BPE 处理的是相邻 token
    pair，并采用确定的非重叠替换顺序。
6.  **认为 byte-level 就没有任何解码问题。** 任意字节序列不一定是合法
    UTF-8；实际 tokenizer 需要保持字节序列和特殊 token 的规范。
7.  **把更短序列等同于更好模型。**
    压缩、鲁棒性、模型质量和系统效率需要分别评估。
8.  **把 toy BPE 的速度当作生产实现的速度。** 简单教学实现并未使用高效
    pair-count 更新结构。

## Part 10 --- 本讲总结

``` text
原始字符串
  └─ tokenizer：选择建模单位
       ├─ 字符级：字符序列
       ├─ 字节级：固定 256 个字节值，序列较长
       ├─ 词级：序列较短，但词表/OOV 代价较大
       └─ 子词 BPE：数据驱动合并，在词表大小与序列长度间折中
  └─ token IDs
       └─ embedding
            └─ Transformer 预测下一个 token
```

必须记住的核心结论：

-   Tokenizer 定义模型"看见"的离散单位。
-   BPE 的核心是统计相邻 pair 并按顺序合并。
-   Tokenization 影响模型输入长度、词表和计算/内存成本。
-   任何关于质量或速度的结论都需要独立测量，不能仅凭 token 数判断。

# 第 12 讲：语言模型评估——指标、基准与有效性

> **课程基准**：Stanford CS336 Spring 2026，Lecture 12 — *Evaluation*（2026-05-06，Percy Liang）。
>
> **官方资料**：[lecture_12.py](https://github.com/stanford-cs336/lectures/blob/main/lecture_12.py)。官方讲义讨论 perplexity、考试类基准、聊天偏好、agentic benchmarks、纯推理与安全评估，以及 realism/validity。下文为原创中文整理。

## 1. 评估不是给模型一个单一分数

“哪个模型更好？”没有脱离目标的唯一答案。模型可能更擅长代码，却在多语言任务上退步；在静态 benchmark 上分数高，却不能稳定完成真实工作流；回答更长、更自信，也未必更正确。

评估首先要明确**构念**：我们真正想测量的能力是什么？随后设计任务、输入、规则、评价器和统计分析，判断观测分数是否能支持这个结论。

至少区分：
- **模型评估**：比较模型的能力或行为；
- **方法评估**：比较训练、提示或推理方法；
- **Agent 评估**：评价模型与工具、环境、记忆和多步决策组成的整体系统。

若把工具权限、搜索能力或执行时间都改变了，就不能把分数差异简单归因于基础模型。

## 2. Perplexity：预训练语言模型的基本指标

对于 token 序列 (x_{1:T})，平均负对数似然为

$$
\operatorname{NLL}(x_{1:T})=-\frac{1}{T}\sum_{t=1}^{T}\log p_\theta(x_t\mid x_{<t}).
$$

Perplexity 定义为

$$
\operatorname{PPL}=\exp(\operatorname{NLL}).
$$

在相同 tokenizer、相同评估语料和相同计数约定下，较低 PPL 表示模型对测试 token 分配了更高的平均概率。PPL 受 tokenizer 与 tokenization 影响，因此不同词表/分词器的 PPL 通常不能直接横向比较。

### 2.1 为什么低 perplexity 不等于所有任务更好？

PPL 评价模型对整段文本的概率分配，许多 token 对具体下游任务并不重要。模型可能对常见格式、标点和背景文字预测得很好，却没有提高数学推理或工具使用能力。PPL 是重要的上游信号，但不是全面的能力指标。

对提示词和回答分开时，可以考虑条件负对数似然 ( -\log p(\text{response}\mid\text{prompt}))，但它仍然受参考答案、tokenizer、长度归一化与数据分布影响。

## 3. 常见 benchmark 类型

| 类型 | 常测内容 | 主要风险 |
|---|---|---|
| 知识/考试 | 学科知识、事实回忆、多选题 | 数据污染、猜测策略、选项格式 |
| 数学/纯推理 | 计算、证明、组合推理 | 答案验证难、提示敏感、训练集泄漏 |
| 代码 | 代码生成、单元测试通过率 | 测试覆盖有限、运行环境与依赖差异 |
| Chat preference | 人类或模型对回答的偏好 | 评审偏差、长度偏好、位置偏差 |
| Agentic | 多步工具使用与环境任务 | 工具权限、环境状态、时间预算影响结果 |
| Safety | 拒答、风险识别、越狱鲁棒性 | 过度拒答、攻击分布有限、评估者偏差 |

选择 benchmark 时，要让它与目标能力匹配，而不是因为某项测试流行就默认它代表通用智能。

## 4. Realism 与 Validity

**Realism（现实性）**：测试任务和环境是否接近实际使用场景。  
**Validity（效度）**：观测分数是否真的支持我们声称测量的能力。

一个 benchmark 可以高度真实但难以精确归因；也可以严格可控但与现实使用相距很远。两者需要权衡。有效评估要说明：
- 任务是否代表目标场景；
- 分数是否受到非目标因素影响；
- 评价规则是否一致、可重复；
- 测试是否泄漏到训练数据；
- 结果是否能推广到其他分布。

## 5. 设计可靠的评估协议

1. **明确目标与比较对象**：基础模型、提示模板、agent、工具链或训练方法。
2. **固定规则**：system prompt、few-shot 示例、temperature、token budget、工具权限和超时。
3. **控制数据污染**：检查公开测试集是否可能进入预训练/后训练语料。
4. **选择评价器**：精确匹配、单元测试、规则 grader、人类偏好或模型裁判。
5. **重复随机过程**：对采样生成任务，使用多个 seed 或足够样本。
6. **报告不确定性**：准确率之外，报告置信区间、分组表现和失败类型。
7. **做错误分析**：区分知识缺失、推理错误、格式错误、工具错误和拒答行为。
8. **发布完整协议**：数据版本、提示、模型版本、解码参数、代码和统计方式。

## 6. 自动评价与模型裁判

自动指标成本低且可重复，但可能只覆盖可形式化的目标。模型裁判可以评价开放式回答，但会受到提示、偏好、答案顺序、长度、表达风格和模型家族偏差影响。

使用模型裁判时，应：
- 随机化候选答案顺序；
- 尽可能使用盲评；
- 通过人类标注样本校准裁判；
- 报告裁判与人类的一致性；
- 评估长度偏差和位置偏差；
- 不把单一裁判的判断当成客观真值。

对数学/代码任务，如果存在可信的精确答案或执行环境，应优先采用可验证 grader，同时检查测试覆盖是否足够。

## 7. Agent 评估的额外难点

Agent 的结果依赖模型、提示、工具、环境、记忆、重试策略和预算。一个任务成功率高的系统，可能是因为允许更多调用或更长运行时间，而不是单步推理能力更强。

应记录每个 episode 的工具调用数、token 数、墙钟时间、成本、成功/失败类别和恢复行为。对非确定性环境，需控制初始状态并重复运行。还要防止 agent 通过利用评测环境漏洞得分，却没有完成任务本意。

## 8. 安全评估不能只看拒答率

拒答过少可能放过有害请求；拒答过多则损害正常使用。应同时测量有害请求的正确拒绝、正常请求的正确帮助、越狱鲁棒性、上下文依赖和误拒率。安全测试集需要多样攻击方式，且应报告测试边界，不能用有限 benchmark 宣称系统绝对安全。

## 9. 统计与数据污染

小样本 benchmark 的分数可能有较大方差。对两个模型的微小差异，需要检查置信区间或成对比较，而不是只比较点估计。对多任务综合分数，应公开权重和聚合方式，避免某些容易任务掩盖关键能力退化。

数据污染可来自训练集直接包含测试题，也可能来自网页讨论、答案解释或近重复样本。污染风险不一定能完全消除，因此应使用新鲜、隐藏或动态生成的评估，并明确数据截止时间。

## 10. 常见误区

- 低 PPL 不代表所有下游任务都更好。
- benchmark 分数不是脱离测试协议的模型固有属性。
- LLM-as-a-judge 不是无偏的真值 oracle。
- 多选题高分可能来自格式/选项偏差。
- agent 评估必须记录工具和预算，否则比较不公平。
- 安全评估要同时考虑误拒与漏拒。
- 只报告平均值会掩盖长尾失败和子群体差异。

## 12. 与作业的联系

A3 的 scaling 实验需要选择稳定、可比较的指标；A4 数据处理可能改变模型的知识与行为；A5 的 SFT/RL/RLVR 需要在训练 reward 之外用独立评估检查泛化与安全。训练 reward 上升不等于真实任务能力一定提升。
